## 1. 배경과 목표

노트가 늘어나면 원하는 노트를 찾기 어렵다. 노트에 태그를 붙이고, 태그로 노트를 걸러 볼 수 있게 한다.

| 목표                                | 성공 기준                                                 |
| ----------------------------------- | --------------------------------------------------------- |
| 노트를 주제별로 표시한다            | 노트 편집 화면에서 태그를 붙이고 뗄 수 있다               |
| 같은 주제의 노트를 빠르게 모아 본다 | 태그를 한 번 클릭하면 그 태그가 붙은 노트만 목록에 남는다 |

## 2. 사용자 시나리오

1. React 공부 노트를 쓰면서 `React`, `공부` 태그를 붙이고 저장한다.
2. 며칠 뒤 사이드바 목록에서 아무 카드의 `React` 태그를 클릭한다.
3. 목록에 `React` 태그가 붙은 노트만 남고, 목록 위에 `#React ×` 필터 표시가 보인다.
4. ×를 눌러 필터를 풀면 전체 노트가 다시 보인다.

## 3. 기능 요구사항

### F1. 메모에 태그 추가/삭제 [사용자]

- 노트 편집 화면(생성·편집 모두)에서 태그를 추가하고 삭제한다.
- 태그는 문자열이고, 같은 노트 안에서 중복을 허용하지 않는다(대소문자 무시).
- 세부 규칙(정규화, 20자·10개 제한, 입력 조작, 저장 시점)은 `spec-fixed.md` 2~4장을 따른다.

### F2. 태그 클릭으로 메모 필터 [사용자]

| 항목             | 요구사항                                                                                                        | 출처                      |
| ---------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------- |

## 4. 기술 결정

### TD-1. 태그 데이터 구조: A안 (`Note.tags: string[]`) [사용자]

> "A안"은 `spec-fixed.md` 작성 전 데이터 구조 질문(Q1)의 첫 번째 선택지로 해석했다. [임의: 해석]

- **상황**: 노트에 여러 개의 문자열 태그를 저장해야 한다. 백엔드는 json-server(`db.json`)라서 별도의 쿼리나 조인 로직을 만들 수 없고, 기존 데이터 흐름(`api/notes.ts` → `NotesContext` → 컴포넌트)은 노트 단위 CRUD만 지원한다.
- **다른 후보**
  - **A안**: `Note` 안에 `tags: string[]` 배열로 저장
  - **B안**: `db.json`에 `tags` 컬렉션을 따로 두고, 노트는 `tagIds: string[]`로 참조
  - **C안**: `tags: "react,공부"`처럼 쉼표로 구분한 문자열 하나로 저장
- **결정**: **A안**. 기존 `PATCH /notes/:id`에 `tags` 배열을 함께 보내 저장한다. `tags`가 없는 예전 노트는 `api/notes.ts`의 `normalizeNote()`에서 `[]`로 보정한다.
- **결과**
  - 장점: 새 API·Context가 필요 없어 변경 범위가 가장 작다(타입 1줄, API 보정, 컴포넌트). 노트를 저장할 때 태그도 함께 원자적으로 저장된다. 원본 정의서의 "태그는 문자열로 저장한다"와 그대로 맞는다.
  - 단점: 태그 이름을 전체 노트에서 한 번에 바꾸려면 모든 노트를 돌며 수정해야 한다(→ 이번에 안 만듦). 전체 태그 목록이 필요하면 모든 노트의 `tags`를 모아서 계산해야 한다. 태그별 색상 같은 속성을 붙일 곳이 없다(→ 이번에 안 만듦). 같은 태그가 노트마다 `React`/`react`처럼 다른 표기로 저장될 수 있다.

### TD-2. 필터 방식: 클라이언트 필터 + `App` 로컬 state [임의]

- **상황**: F2의 필터는 화면 상태다. `NotesContext`는 이미 전체 노트를 메모리에 가지고 있다. 대소문자를 무시하는 배열 포함 검색은 json-server 쿼리로 표현하기 어렵다(검증하지 않음).
- **다른 후보**
  - **서버 필터**: `GET /notes?...`로 걸러서 받기 → 대소문자 무시 비교를 서버에서 맞추기 어렵고, 필터를 바꿀 때마다 다시 요청해야 한다. 이미 받은 데이터를 다시 요청하는 셈이다.
  - **Context에 필터 상태 두기**: `NotesContext`에 `activeTag` 추가 → CLAUDE.md의 "서버 데이터 = Context, 화면 상태 = App" 규칙에 어긋난다.
  - **URL 쿼리(`?tag=React`)에 저장**: 새로고침·공유에 유리하지만 라우터가 없고, 이번 범위에 비해 크다.
- **결정**: `App`에 `activeTag: string | null` state를 두고 `NoteList`에 props로 내린다. `NoteList`에서 `notes.filter((n) => hasTag(n.tags, activeTag))`로 거른다. 비교 함수는 `src/utils/tags.ts`의 `hasTag`(대소문자 무시)를 재사용한다.
- **결과**
  - 장점: 서버 요청이 없어 필터가 즉시 바뀐다. 기존 상태 계층 규칙을 지킨다. F1의 중복 판단과 같은 비교 함수를 써서 동작이 일관된다.
  - 단점: 새로고침하면 필터가 풀린다. 노트가 아주 많아지면 매 렌더마다 전체 배열을 거른다(현재 규모에서는 문제 없음). `App`의 props가 하나 더 늘어난다.

## 5. 이번에 안 만들 것 [사용자]

| 항목                   | 이유 / 나중에 만든다면                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------------------------- |
| 태그 색상              | 모든 태그는 노랑 파스텔 하나(디자인 시스템 D-012). A안 구조에는 색을 저장할 곳이 없다 → B안 전환이 필요    |
| 태그 이름 수정         | 노트 안의 태그는 지우고 다시 추가하면 된다. 전체 노트에서 이름을 일괄 변경하려면 모든 노트를 수정해야 한다 |
| 자동완성               | 입력 중 기존 태그 추천 없음. 만든다면 전체 노트의 `tags`를 모아 계산한다                                   |
| 태그 여러 개 동시 필터 | 필터는 한 번에 태그 하나(F2). AND/OR 조건 UI가 필요해져 범위가 커진다                                      |
